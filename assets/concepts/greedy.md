# Greedy

找零 30 元，手上的硬幣有 1、5、10、25 四種，要用最少的枚數。

沒有人會把所有組合列出來再挑。直覺的做法是先拿 25，剩 5，再拿一枚 5，結束，兩枚。從最大的開始拿，拿到不能再拿為止，中途沒有回頭改過主意。

這就是 greedy：每一步挑當下看起來最好的，選了就不再更動。

問題是這樣為什麼會對。

---

## 它不是「拿最大」

找零這個例子的規則剛好是拿最大的，但那是題目給的規則，不是 greedy 這個技巧規定的。換一題規則就完全不同：

- Huffman 編碼：每次合併頻率**最小**的兩個
- 會議室排程：跟大小無關，按結束時間排
- Jump Game：跟大小無關，維護「目前能到的最遠位置」

Greedy 真正的動作是**每一步只留一條路，其他當場丟掉**。DP 剛好相反，它每一步把所有選項都留著，最後才比。

拿 House Robber 的 `[2, 3, 2]` 對照。DP 在每一格保留兩個答案：

```
i=0   搶這間=2   不搶這間=0
i=1   搶這間=3   不搶這間=2
i=2   搶這間=4   不搶這間=3      ← 這格的「搶」用到了 i=0 的「搶」
最後  max(4, 3) = 4
```

走到 `i=2` 的時候，`i=0` 那格「搶了 2」的那條線還活著，所以 `2 + 2 = 4` 組得出來。

Greedy 只留一條：

```
掃過去最大的是 3 → 拿 3
index 0 跟 index 2 都變成鄰居，封鎖
沒得拿了 → 3
```

第一步拿了 3，「不拿 3」那整條線當場消失，而 4 就藏在那條線裡面。

所以判斷一份 code 是 greedy 還是 DP，看的不是它怎麼選，是選完之後其他選項還在不在。還在、最後才比，那是 DP；當場丟掉不再回頭，那是 greedy，而且要負責證明丟掉的不可能更好。

## 先看它什麼時候是對的

用 Go 把找零寫出來，從最大的幣值開始拿：

```go
func coinChangeGreedy(coins []int, target int) int {
    sort.Sort(sort.Reverse(sort.IntSlice(coins))) // 由大到小

    n := 0
    for _, c := range coins {
        for target >= c { // 拿到不能再拿
            target -= c
            n++
        }
    }
    if target > 0 {
        return -1 // 湊不出來
    }
    return n
}
```

開頭那組餵進去，它照樣拿 25 + 5。日常用的幣值都是這個結果，換誰來湊都是最少枚數。

換一組幣值就壞了：

```
幣值 [1, 3, 4] 湊 6

greedy：先拿 4，剩 2，只能 1 + 1     → 4 + 1 + 1，三枚
最佳  ：                            → 3 + 3，  兩枚
```

同一份 code，同一個「拿最大的」規則。差別在幣值本身。

## 兩個條件

Greedy 能用要滿足兩件事。第一件跟 [DP](/concept/dp) 共用，第二件是 greedy 專屬的。

### 最佳子結構

大問題的最佳解，可以由子問題的最佳解組成。找零湊 30 的最佳解，扣掉第一枚 25 之後，剩下的必須是「湊 5 的最佳解」。要是拆開之後子問題的最佳解拼不回大問題的最佳解，那 greedy 跟 DP 都免談。

### 貪心選擇性質

當下看起來最好的那個選擇，可以證明它一定屬於某一個全域最佳解。

`[1, 5, 10, 25]` 有這個性質：湊 30 的最佳解裡面一定有一枚 25。因為要是不用 25，剩下只能用 10 跟 5 湊 30，至少要三枚，比「25 加一枚」還多。

`[1, 3, 4]` 沒有：湊 6 的最佳解 `3 + 3` 裡面根本沒有 4。拿了 4 就注定用三枚。

所以 greedy 錯不是因為它笨，是因為題目沒給它那個保證。

## 怎麼確認貪心選擇性質成立

用反證，這個手法叫 exchange argument：假設有一個最佳解沒有用到我的貪心選擇，那就把它換成我的選擇，證明換完之後不會變差。換得成，代表我的選擇至少跟最佳解一樣好。

會議室排程是最乾淨的例子。給一堆會議的起訖時間，同一間會議室最多能排幾場不重疊的？

貪心規則：**每次挑結束最早的那場。**

```go
type meeting struct{ start, end int }

func maxMeetings(ms []meeting) []meeting {
    sort.Slice(ms, func(i, j int) bool {
        return ms[i].end < ms[j].end // 照結束時間排，早結束的先
    })

    picked := []meeting{}
    lastEnd := 0
    for _, m := range ms {
        if m.start >= lastEnd { // 跟上一場不重疊才收
            picked = append(picked, m)
            lastEnd = m.end
        }
    }
    return picked
}
```

交換論證長這樣：設最佳解排了 k 場，第一場是 A。我的貪心挑的是結束最早的 B，所以 B 的結束時間不會晚於 A。把最佳解裡的 A 換成 B，後面那 k-1 場原本就都在 A 結束之後開始，B 結束得更早，所以它們照樣塞得下。換完還是 k 場，沒有變差。同樣的論證套用到第二場、第三場，一路下去。

「結束最早」是唯一站得住的規則。另外兩個直覺一樣的規則都會失敗：

```
四場會議 (0,10) (1,3) (4,6) (7,9)

照最早結束挑   (1,3) (4,6) (7,9)   3 場   ← 最佳
照最早開始挑   (0,10)              1 場   第一場就佔掉整個時段
```

```
三場會議 (0,5) (4,6) (5,10)

照最早結束挑   (0,5) (5,10)        2 場   ← 最佳
照時間最短挑   (4,6)               1 場   它卡在中間，兩邊都排不下
```

三個規則都符合「挑當下最好的」這個描述。差別在只有第一個證明得出貪心選擇性質。所以 greedy 難的從來不是寫 code，是選對那個規則，而且證明它。

## 為什麼手動試幾組不算驗證

House Robber（[#198](/problem/house-robber)）不能用 greedy。貪心規則「每次拿最大的、旁邊兩間就不能拿」在 `[2, 3, 2]` 就錯了：拿 3 得 3，正確答案是 2 + 2 = 4。

但這題 LeetCode 給的兩組範例，貪心全部答對：

```
[1, 2, 3, 1]     貪心 4    正解 4
[2, 7, 9, 3, 1]  貪心 12   正解 12
```

隨機輸入跑 20000 組，看貪心跟 DP 答案相同的比例：

| 陣列長度 | 貪心剛好答對的比例 |
|---|---|
| 3 | 85.4% |
| 5 | 80.4% |
| 10 | 68.6% |
| 20 | 45.0% |

長度 3 有八成五會過。心算隨手試兩三組短的，幾乎不可能撞到反例，而 `[2, 3, 2]` 正是那 14.6% 裡面的一種。要到長度 20 錯誤率才過半，那個規模已經不是手算會去試的。

所以「先猜 greedy、拿範例驗一下」這條路本身就不可靠：範例的規模剛好落在貪心最容易矇對的區間。真要驗，只能寫一份暴力或 DP 當對照組跑隨機對拍。

---

## 跟 DP 的分工

Greedy 不是 DP 的一種，兩個是不同技巧，共用最佳子結構這個前提。方向是單向的：**能用 greedy 的題目，DP 一定也解得出來，只是慢；反過來不成立。**

`[1, 5, 10, 25]` 用 DP 湊 30 也會得到兩枚，只是它把所有組合都試過。`[1, 3, 4]` 只有 DP 答得對。

實務上的順序是先想 DP，因為它一定對。想清楚狀態轉移之後，再問「每一步的最佳選擇會不會被後面推翻」，答案是不會，才降級成 greedy 換速度。倒過來先猜 greedy，就會踩到上一節那個統計。

## 常見的 greedy 題型

| 題型 | 貪心規則 | 為什麼成立 |
|---|---|---|
| 會議室排程 | 挑結束最早的 | 換掉最佳解的第一場不會變差 |
| 區間合併 | 照起點排序後掃描 | 重疊的區間一定相鄰 |
| Jump Game | 記住目前能到的最遠位置 | 能到 i 就能到 i 之前的每一格 |
| 分糖果 / 分餅乾 | 兩邊都排序後配對 | 最小的需求配最小的供給不會浪費 |
| Huffman 編碼 | 每次合併頻率最小的兩個 | 頻率最小的兩個一定在樹最深處 |

每一列的第三欄都是一句交換論證的縮寫。寫不出第三欄，就代表還沒證明，那個 greedy 只是猜的。

## 總結

| | Greedy | DP |
|---|---|---|
| 需要最佳子結構 | 是 | 是 |
| 需要貪心選擇性質 | 是 | 否 |
| 每一步 | 選一個，不回頭 | 所有選項都試，留最好的 |
| 時間 | 通常 $O(n)$ 或 $O(n \log n)$（排序） | 通常 $O(n \times 狀態數)$ |
| 空間 | 通常 $O(1)$ | 通常 $O(n)$ 以上 |
| 寫錯的症狀 | 輸入短的時候全過，輸入一長答案就偏小 | 通常直接 TLE 或 MLE |

Greedy 快，代價是要先證明它為什麼對。證不出來就不要用，因為它錯的時候不會報錯，只會安靜地給你一個比較差的答案。
