# 規模直覺

題目給「一百萬個整數，值在 0 到 10 億之間，記憶體有限」。這時要判斷的是：這些資料吃多少記憶體、什麼複雜度會超時、10 億這範圍有沒有暗示。

這篇談的是「看到數字時腦袋要跳出什麼」，不是演算法本身。記憶體、時間、複雜度三個錨點背起來、用乘除推，再配一張 magic number 對照表看暗號。

---

## 錨點 1：記憶體

先記兩個換算，其他用乘除推：

- **`8 bits = 1 byte`** — 固定的，不會變。
- **`1 個 int = 4 bytes = 32 bit`** — Java、C#、多數 C 平台的預設。

例外比想像中多，而且刷題最常用的兩個語言都是例外：

| 語言 | 一個整數 | 100 萬個 |
|---|---|---|
| Java、C#、C 的 `int` | 4 bytes | 4 MB |
| Go 的 `int` | **8 bytes**（word size，要 4 得寫 `int32`） | 8 MB |
| JS 的 `Array` | 沒有 int，一個 8 bytes | **8 MB** |
| JS 的 `Int32Array` | 4 bytes | 4 MB |
| Python 的 `int` | 任意精度，小整數約 28 bytes | 28 MB 以上 |

背 4 MB 那格，其他從它推。**用 JS 的話背 8 MB**，因為 `new Array()` 配出來的每一格就是 8 bytes，要 4 MB 得改用 `Int32Array`。

**怎麼來**：1 個 int = 4 byte，100 萬 × 4 = 4,000,000 byte ≈ 4 MB。JS 的 number 是 8 bytes，同樣 100 萬筆就是 8 MB。

實測對得上：Node v22.22.3 開 `--expose-gc`，`new Array(1e6)` 填 0 到 999999，強制回收前後的 `heapUsed` 差 7.64 MB。陣列改填小數（`i + 0.5`）是 7.63 MB，兩種值一樣大，因為 V8 對這個大小的陣列都用 8 bytes 一格。比推算的 8.00 MB 少 4.5%，V8 內部的表示法沒有那麼死板，所以背 8 MB 是安全的上界。

往上 ×10（這張是 **4 bytes** 那一列，用 JS 全部 ×2）：

| 量 | Java / C 的 int | JS 的 Array |
|---|---|---|
| 100 萬 | 4 MB | 8 MB |
| 1 千萬 | 40 MB | 80 MB |
| 1 億 | 400 MB | 800 MB |
| 10 億 | **4 GB** ← 一般筆電開始吃力 | 8 GB ← 已經爆了 |
| 100 億 | 40 GB ← 必須外部排序 | 80 GB |

**換型別**：long ×2、bool ÷4。`char` 要看語言：C 的 `char` 是 1 byte（÷4），Java 的 `char` 是 2 bytes（÷2，UTF-16 的一個 code unit）。

**對比熟悉的東西記得久**：

| 大小 | 像什麼 |
|---|---|
| 4 MB | 一張高解析度照片 |
| 400 MB | 一部 720p 短電影 |
| 4 GB | 一部 1080p 電影 |
| 40 GB | 整季美劇 |

## 錨點 2：執行時間

「一個操作」有多快，看那是什麼操作。同一台機器量 Node，一秒能做幾次：

| 操作 | 一秒幾次 |
|---|---:|
| 純迴圈（加減、位移、比較） | 10.2 億 |
| 陣列順序寫入（篩法那種） | 2.84 億 |
| Map 插入加查詢（各半，map 長到 100 萬筆） | 530 萬 |

排序不在這張表裡，它不能寫成「每秒幾次」，理由在下面。

最快跟最慢差 192 倍。所以拿同一個數字估所有題目，一定有一邊會錯得很遠：

| 操作數 | 純迴圈 | 陣列順序寫入 | Map |
|---|---|---|---|
| $10^4$ | 10 μs | 35 μs | 2 ms |
| $10^7$ | 10 ms | 35 ms | 1.9 秒 |
| $10^8$ | 98 ms | 352 ms | 18.8 秒 |

先問這題的時間主要花在哪一欄，再看那一欄。

- $10^8$ 次純迴圈跑 98 ms，**過得了**
- $10^7$ 次 Map 操作要 1.9 秒，**超時**

這兩件事都跟「$10^7$ 是安全線」相反。舊版這一節寫的是單一數字 $10^7$，那個數字其實只對 Map 那一欄接近，用在純迴圈的題目上會低估自己能做多少，差到 100 倍。

**這張表只到 $10^8$，不要往下外推。** Map 那一欄量的是「插入 $10^6$ 次加查詢 $10^6$ 次，map 從 0 長到 100 萬筆」的混合速率。$10^{10}$ 次照同樣比例就是 50 億筆的 map，16 GB 裝不下，那格不是慢，是根本跑不完。純迴圈跟陣列那兩欄外推沒有這個問題，但 Map 這欄的每一格都預設 map 停在 100 萬筆左右。

### 排序不套上面那張表，直接查

排序不套「每秒幾次操作」，直接記時間。整數資料放在一般 `Array` 裡，用 `sort((a,b)=>a-b)`：

每一格都跑 15 次，丟掉第 1 次，剩下 14 次取中間那個數當結果。IQR 那欄是這 14 次彼此差多遠：由小排到大，中間那一半的頭尾差多少，再除以中位數。1% 就是每次跑都差不多；到了 10%，那格就只能當量級看，不能當一個準的數字。

| 排幾筆 | 時間 | IQR | 每筆 |
|---|---:|---:|---:|
| $10^5$ | 17.7 ms | 2.0% | 177 ns |
| $10^6$ | 216 ms | 1.0% | 216 ns |
| $10^7$ | **2481 ms** | 3.6% | 248 ns |

心算抓 **300 ns 一筆**，$10^5$ 到 $10^7$ 都套這個就行。

**但先問資料放在哪個容器。** 同樣 $10^7$ 筆、同一份資料，只換容器：

| 怎麼排 | 時間 | IQR | 對第一列 |
|---|---:|---:|---:|
| `Array` 配 `(a,b)=>a-b` | 2481 ms | 3.6% | 1.0 |
| `Float64Array.prototype.sort()` | 1012 ms | 2.1% | 2.5 倍快 |
| `Int32Array.prototype.sort()` | **624 ms** | 4.8% | **4.0 倍快** |

這個差距我沒拆開量，可能的來源：

- `Array` 的每次比較是一次 JS 函式呼叫，typed array 的 `sort()` 全程不進 JS
- `Array` 存的是 tagged 值，`Int32Array` 是連續的 4 bytes

題目給你 `number[]` 直接 `sort` 就是第一列。整數先 `Int32Array.from(nums)` 再排是第三列，錨點 1 為了省記憶體推的也是 `Int32Array`。

**值是整數還是小數也有差，跟容器是兩件事。** 同一個 `Array`、同一個 comparator、$10^6$ 筆，只把每個值加 0.5 變成小數：

| 值域 | 整數 | 小數 | 小數／整數 |
|---|---|---|---:|
| 0 到 $2\times10^9$ | 214 ms（IQR 0.8%） | 466 ms（IQR 3.4%） | 2.2 |
| 0 到 $10^6$ | 274 ms（IQR 1.2%） | 468 ms（IQR 10.0%） | 1.7 |

兩邊的 backing store 都是 7.64 MB，V8 對這個大小的陣列都用 8 bytes 一格。不是陣列變大，是每次比較本身變貴。

**但那個倍數不準，只能當量級看。** 小數那一欄的 IQR 是 3.4% 跟 10.0%，換一次執行再量一次，數字還會不一樣；同一個比值前後量到 1.2、1.5、1.7、1.8、2.2、2.6。能講的是「小數比整數貴，大概一到兩倍多」，不能講一個小數點後一位的數字。

整數那一欄反而很穩（IQR 不到 1.5%）。這一欄有件事我看不懂：值只到 100 萬的那組 274 ms，值散到 20 億的那組 214 ms，小的那組反而慢 28%。重跑三次都是這個方向。為什麼，沒查。

**heap 不查這張表。** 手寫二元 heap（一個 `Array`，siftUp / siftDown），push $10^6$ 次加 pop $10^6$ 次是 **150 ms**，同樣 $10^6$ 筆的 `Array.sort()` 是 216 ms。heap 的比較次數是排序的 2 倍，時間只有 0.70 倍。原因跟容器那張表一樣：比較寫在迴圈裡，沒有函式呼叫。segment tree 沒量過。

**每筆變貴的速度，就是 $\log n$ 而已。** 從 177 ns 爬到 248 ns，1.40 倍；$\log_2 n$ 從 16.61 到 23.25，算出來也是 1.40 倍。

這次剛好對上，但別當成證明。前一次同一支腳本量到的是 1.46 倍，而兩個端點的 IQR 是 2.0% 跟 3.6%，複合的不確定度就有那個量級。**能說的只有「在這個規格下看不出超過 $\log n$ 的成長」，不能說「$O(n\log n)$ 解釋得完」。** 要下後面那句得把樣本數再往上加。

那比較的次數呢？

| $n$ | 實際呼叫 comparator | $N\log_2 N$ | 比值 | $\log_2(n!)$ 下界 | 對下界 |
|---|---:|---:|---:|---:|---:|
| $10^5$ | 152.9 萬 | 166.1 萬 | 0.921 | 151.7 萬 | 1.008 |
| $10^6$ | 1861 萬 | 1993 萬 | 0.933 | 1849 萬 | 1.006 |
| $10^7$ | 2.196 億 | 2.325 億 | 0.944 | 2.181 億 | 1.007 |

$\log_2(n!)$ 是比較排序的理論下界，任何比較排序都不可能低於它。TimSort 在亂數上只比下界多 0.7%。

**所以排序慢，不是慢在比較的次數，是慢在每一次比較。** 一次比較要多久，看資料放在哪個容器、值是整數還是小數。容器最多差 4.0 倍（`Array` 對 `Int32Array`），型別差一到兩倍多。手上是整數就別讓它變成小數，這個不用換容器就有效。

實測條件：Apple M1 Pro、Node v22.22.3、2026-08-06。上面全部同一個規格：單一 process、每格跑 15 次、丟第 1 次、剩下 14 個樣本取中位數配 IQR。比較次數那張是確定性的，跑一次就夠。腳本兩支，在 scotch 的 `bench/lang-ops-per-sec/diag-sort`。

規格一度只跑 5 次（4 個樣本），那時同一格重跑的全距佔中位數 27%，而這一節有一個結論需要 4% 的解析度。樣本數拉到 14 之後，整數那些格的 IQR 收到 1% 到 5%，夠報那張表，還是不夠斷言 4% 那件事。小數那幾格收不下來，所以那裡只給量級。

資料是 0, stride, 2·stride… 洗牌，相異值保證等於 $n$，值域撐到 $2\times10^9$ 量級。

腳本在 scotch 的 `bench/lang-ops-per-sec/diag-sort`，前 3 欄在 `bench/lang-ops-per-sec`。

**這一節的數字重跑過三次。** 第 1 版自己寫的 LCG 乘積超過 $2^{53}$，$n=10^7$ 只產出 16,403 個相異值，99.84% 重複，而 TimSort 專門吃重複資料。當時量到的比較數甚至低於 $\log_2(n!)$ 那條下界，那是不可能的事，我沒查就寫進來了。第 2 版換了產生器但用小數當值，量到的每筆成本比 $\log n$ 多漲 50%，我去追那 50% 從哪來，追了兩支腳本才發現是型別造成的。現在的腳本每次跑之前先驗相異值等於 $n$，對不上就 throw。

為什麼 Map 慢這麼多，沒有量。**合理的猜測**是 100 萬筆裝不進 CPU 快取，每次查都要跑一趟主記憶體，但這輪沒有收集任何 cache miss 計數，所以它只是猜測。題目的 map 如果只有幾千筆，整張表待在快取裡應該會快很多，快多少也沒量過。

時間單位每階差 1000 倍：1 秒 = 1000 ms = $10^6$ μs = $10^9$ ns。

常見判題碼：

| 判題碼 | 全名 | 意思 |
|---|---|---|
| AC | Accepted | 通過 |
| TLE | Time Limit Exceeded | 超時（超過時間上限，答案對也算失敗） |
| MLE | Memory Limit Exceeded | 記憶體超標 |
| WA | Wrong Answer | 答案錯 |
| RE | Runtime Error | 執行時出錯（越界、除以 0…） |

## 錨點 3：輸入大小 → 允許複雜度

把錨點 2 反過來用：題目給 N，**腦袋直接知道哪些複雜度會 TLE**。

前 8 列的 N 是**陣列長度**，最後 2 列的 N 是**數值範圍**。$10^{18}$ 個元素不存在，那一列講的是在值域上二分，不是掃過 $10^{18}$ 筆資料。

| 陣列長度上限 | 允許的最壞複雜度 | 典型解法 |
|---|---|---|
| ≤ 10 | $O(N!)$ | 全排列 / 暴力 backtracking |
| ≤ 20 | $O(2^N)$ | bitmask DP / subset |
| ≤ 100 | $O(N^4)$ | 4 層迴圈 |
| ≤ 1,000 | $O(N^3)$ **邊緣**，實測約 1.5 秒 | 3 層迴圈 / Floyd-Warshall |
| ≤ $10^4$ | $O(N^2)$ | 雙迴圈 / DP |
| ≤ $10^5$ | $O(N \log N)$ | sort / heap / segment tree |
| ≤ $10^6$ | $O(N \log N)$ 邊緣，最好 $O(N)$ | 線性掃 / monotonic stack |
| ≤ $10^7$ | $O(N)$ | 一遍掃完 |

| 數值範圍上限 | 允許的最壞複雜度 | 典型解法 |
|---|---|---|
| ≤ $10^9$ | $O(\log N)$ | 在值域上二分 / 數學公式 |
| ≤ $10^{18}$ | $O(\log N)$ | 大數除非數學特解 |

$N=1000$ 配 $O(N^3)$ 那格是實跑的：Floyd-Warshall 的內圈跑滿 $10^9$ 次，用 `Int32Array` 存，量到 1437 到 1590 ms。換成一般 `Array` 只會更慢。題目真的給 $N=1000$ 又要三層迴圈的話，得看判題機給多少秒。

**讀題流程**：看到 $N=10^5$ → 腦袋自動排除 $O(N^2)$，往 $O(N \log N)$ 想。

**梯子記法**：N 漲 100 倍，能容忍的複雜度就退一階。

- $N=10^5$ → $O(N \log N)$
- $N$ ×100 到 $10^7$ → $O(N)$
- $N$ ×100 到 $10^9$ → $O(\log N)$（不能再線性掃了）

**為什麼是這條梯子**：每一列看內圈在做什麼，套錨點 2 對應的那一欄。$O(N\log N)$ 那三列的內圈是排序，直接查排序表；$O(N^2)$ 的雙迴圈內圈是加減跟比大小，走純迴圈那欄；$O(N)$ 一遍掃完是循序讀寫陣列，走陣列那欄。

| | 內圈在做什麼 | 操作數 | 時間 | |
|---|---|---:|---:|---|
| $N=10^5$ 配 $O(N^2)$ | 純迴圈 | $10^{10}$ | 9.8 秒 | TLE |
| $N=10^5$ 配 $O(N \log N)$ | 排序 | 查表 | 18 ms | 過 |
| $N=10^6$ 配 $O(N \log N)$ | 排序 | 查表 | 216 ms | 過 |
| $N=10^7$ 配 $O(N \log N)$ | 排序 | 查表 | **2.5 秒**（`Array`）／**0.62 秒**（`Int32Array`） | 看容器 |
| $N=10^7$ 配 $O(N)$ | 陣列順序寫入 | $10^7$ | 35 ms | 過 |

$N=10^7$ 那列是這條梯子的邊界，而且**它的判定看你把資料放哪**。用一般 `Array` 配 comparator 是 2.5 秒，超時，所以梯子把 $10^7$ 那格寫成只剩 $O(N)$。整數資料改用 `Int32Array` 是 0.62 秒，$O(N\log N)$ 過得了。

所以 $10^7$ 配排序那格預設超時，但值是整數而且先搬進 `Int32Array` 的話仍然可行。梯子表上寫的是預設值。

上面的梯子表把 $10^6$ 那列標成「$O(N\log N)$ 邊緣」，實測卻是 216 ms，離 1 秒還很遠。那個「邊緣」留著，因為判題機比筆電慢，而且真實解法除了排序還有別的事要做。當成安全邊界讀，不是當成實測值。

排序那三列是實跑的，不是從操作數推的，所以「操作數」欄寫「查表」。排序花多久要看容器，不能用一個次數乘一個常數算出來，原因在錨點 2。

直覺公式：**時間預算抓 200 ms**，換算成各欄的操作數上限：

| 內圈在做什麼 | 操作數上限 |
|---|---|
| 純迴圈 | $2 \times 10^8$ |
| 陣列順序寫入 | $5 \times 10^7$ |
| 排序 | 查表（約 80 萬筆） |
| Map 存取 | $10^6$ |

舊版寫的是一句「N × 對應複雜度 ≤ $10^7$」，一個數字蓋四種內圈。那個 $10^7$ 拿去套哪一欄都差 10 倍以上，套排序也一樣（排序的每次比較實測 11.5 ns，$10^7$ 次比較是 115 ms，而 $10^7$ 筆排序本身要 2.5 秒 —— 「操作數」在排序上根本不是同一個東西，一筆的成本包含 20 幾次比較）。200 ms 這個預算留了 5 倍餘裕給判題機比筆電慢的部分。

**這張梯子的前提是 JS。** 換語言要乘倍率，同一個純迴圈 Go 比 Node 快 1.5 倍，CPython 慢 77 倍（[SRC: `scotch/bench/lang-ops-per-sec/RESULTS.md`]）。用 CPython 的話整條梯子的 N 上限要往下挪一到兩階。

**心算 $\log_2 N$**：唯一要記的是 $\log_2(10) \approx 3.32$，其他用乘法。

```
log₂(10^k) ≈ 3.3 × k
```

| $N$ | $\log_2 N$ |
|---|---|
| $10^3$ | 10 |
| $10^5$ | 17 |
| $10^7$ | 23 |
| $10^9$ | 30 |
| $10^{18}$ | 60 |

口訣：**N 每多一個 0，log 多 3.3**。

## magic number 對照表

題目裡藏著的數字常常是**結構暗號**。

| 數字 | 暗號 |
|---|---|
| $10^9 + 7$ 或 `998244353` | 答案要 mod，**鎖定 DP 計數題** |
| `26` | 26 個小寫英文字母，**用 array 取代 hashmap** |
| `52` | 大小寫英文字母 |
| `128` / `256` | ASCII 全集 |
| `32` / `64` | bit 操作 / int / long bit 數 |
| `'a' = 97` / `'A' = 65` | ASCII，`'a' - 'A' = 32` |
| $2^{31} - 1 \approx 2.1 \times 10^9$ | int 上限（看到 $10^9$ 量級別怕，long 才 overflow） |
| $2^{53} - 1 \approx 9 \times 10^{15}$ | JS Number 安全整數上限 |
| `null / -1 / Infinity` | 哨兵值，看到題目允許用就考慮 |

**為什麼題目要 mod**：DP 計數題的答案長得很快（費氏 F(100) 已經 $10^{20}$，超過 long 上限 $9 \times 10^{18}$）。所以題目要求 `% (10^9+7)`，把結果收回 int 範圍。

**為什麼是 $10^9+7$ 不是隨便一個數**：

1. 是質數 → 配合「模逆元」做除法時數學才成立
2. $(10^9+7)^2 \approx 10^{18}$，比 long 上限小 → 兩個 mod 過的數相乘不溢位
3. 競賽社群默契，題目慣用

寫 code 時每步 `% MOD`：

```js
const MOD = 1e9 + 7;
dp[i] = (dp[i-1] + dp[i-2]) % MOD;
```

看到題目寫 "return the answer **modulo $10^9+7$**" → **直接判定 DP 計數題**。

## 怎麼用

拿到一題，先讀這幾個地方：

- $N$ 的上限，套錨點 3，就知道還剩哪些複雜度可以用
- 資料量乘上每個元素多大，套錨點 1，就知道記憶體夠不夠
- 題目裡有沒有特殊數字，查 magic number 表，那通常在暗示結構

例：「$N=10^5$ 個整數，找兩數之和等於 target」

```
N=10^5 → 允許 O(N log N) 或 O(N)
記憶體：10^5 × 8 byte = 0.8 MB（JS 的 Array；用 Java 是 0.4 MB）→ 沒壓力
沒有 magic number
→ 走 O(N) 的 hashmap 或 O(N log N) 的雙指標
```

選 hashmap 之前看一下錨點 2 的 Map 那欄：$10^5$ 次 Map 存取是 19 ms，過得了。$N$ 如果變成 $10^7$，同一個 hashmap 解法要 1.9 秒；先排序再走雙指標，用一般 `Array` 是 2.5 秒，改用 `Int32Array` 是 0.62 秒。這時候雙指標那條反而是唯一過得了的，前提是值都是整數。

例：「給 1 兆個整數要排序，記憶體 1 GB」

```
1 兆 int = 4 TB（JS 是 8 TB）→ 完全塞不進記憶體
→ 必須外部排序（K-way merge sort）
```

這題哪個語言都一樣，差 2 倍改不了「塞不進 1 GB」這件事。記憶體錨點的語言差異只在邊界附近才會翻轉結論。

---

## 收尾

三個錨點：100 萬 int = 4 MB（JS 的 Array 要記 8 MB）、排序一筆 300 ns、N 對應複雜度表。其他用乘除推，再配 magic number 表認出題目埋的提示。

時間那個錨點要記**四個數字**，不是一個：純迴圈每秒 10 億、陣列順序寫入 2.8 億、Map 存取 530 萬、排序一筆 300 ns。先問內圈在做哪一種，再套。

排序那 300 ns 有三個前提，換掉任何一個，那個數字就不準了：

- 資料在一般 `Array`：換成 `Int32Array.sort()` 快 4.0 倍
- 值是整數：變成小數慢一到兩倍多
- 比較走 JS 的 comparator：手寫 heap 把比較寫在迴圈裡，比排序便宜

「排序很貴」貴的是這三個前提，不是排序本身。
